# Database Schema — AI Chat Application (Oracle)

This document describes the existing Oracle database schema for the AI chat
application, discovered by direct inspection of the live database on 2026-08-18.

- **Connection:** `chatbot/chatbot@192.168.1.42:1521/pdb.oracle.ek` (PDB: `pdb.oracle.ek`)
- **Schema owner:** `CHATBOT`
- **Tables:** 11 (plus 2 orphaned `MESSAGE_GENERATIONS` copies in the recycle bin,
  which must never be touched). `USER_PERSONAS` and `OTP_LOG` were added after the
  original inspection — see each table's note for when and why
- **Table/column comments:** none defined in the dictionary
- **Triggers:** none
- **Application history:** the schema started near-pristine — only seed rows existed in
  `PROVIDERS`, `AI_ENDPOINTS`, `AI_MODELS`, `CHARACTERS`. The application has been running
  against it since, so `USERS`, `CONVERSATIONS` and `MESSAGES` hold real data.

> **Important:** Do not drop, recreate, truncate, or alter this schema. The schema is the
> source of truth; the application adapts to it.

---

## Entity-Relationship Overview

```text
                        ┌──────────────┐
                        │  PROVIDERS   │  ("DeepSeek", "OpenAI", "Anthropic", …)
                        └──────┬───────┘
                               │ provider_id
                        ┌──────▼───────┐      ┌────────────────┐
                        │  AI_MODELS   │──────│  AI_ENDPOINTS  │  (base_url + api_key)
                        └──┬───────┬───┘      └────────────────┘
              default_model│       │ model_id
                    ┌──────▼───┐   └──────────────────────────┐
                    │  USERS   │                              │
                    └──┬───────┘                              │
                       │ user_id                              │
            ┌──────────▼───────────────┐            ┌─────────▼────────┐
            │      CONVERSATIONS       │            │  MESSAGE_        │
            │  user_id, character_id,  │            │  GENERATIONS     │
            │  model_id, title, status │            │  (usage/telemetry│
            └──────┬───────────────────┘            │   per AI reply)  │
                   │ conversation_id                └─────────▲────────┘
            ┌──────▼────────────┐                                │ message_id
            │     MESSAGES      │────────────────────────────────┘
            │  role, content    │
            └───────────────────┘

   ┌──────────────┐     ┌───────────────────────────────┐
   │  CHARACTERS  │◄────┤  MEMORIES (user × character)  │──► optional message_id → MESSAGES
   │  (personas)  │     │  content, type, importance…   │
   └──────────────┘     └───────────────────────────────┘
```

The schema is a complete AI-chat data model:

| Concept | Where it lives |
|---|---|
| User accounts | `USERS` |
| Authentication | `USERS.PASSWORD_HASH` (single hash column — no salt/algorithm columns; the hashing algorithm is a property of the application, chosen to be Argon2id) |
| Passwords | Hashed (Argon2id, PHC string) in `USERS.PASSWORD_HASH VARCHAR2(255)` |
| AI characters / personas | `CHARACTERS` (name, system_prompt = persona/system prompt, avatar_url, status) |
| Conversations | `CONVERSATIONS` (bound to user + character + model; title; status; timestamps) |
| Messages | `MESSAGES` (conversation_id, role, CLOB content, created_at) |
| AI response telemetry | `MESSAGE_GENERATIONS` (tokens, latency, temperature, purpose) |
| Long-term memory | `MEMORIES` (user × character, content, type, importance, confidence, status, optional link to source message) |
| Provider/model configuration | `PROVIDERS` → `AI_MODELS` → `AI_ENDPOINTS` (base_url + api_key stored in DB) |
| Soft deletion | `STATUS` columns on `USERS`, `CHARACTERS`, `CONVERSATIONS`, `MEMORIES` (see conventions below) |
| Timestamps | `CREATED_AT`/`UPDATED_AT`/`LAST_*_AT` `TIMESTAMP(6)` on most tables |

## Tables

All `ID` columns are `NUMBER(22)` **identity columns** (`GENERATED BY DEFAULT AS IDENTITY`),
backed by automatically created sequences `ISEQ$$_xxxxx` (cache 20, no cycle).
Every table's `ID` is `NOT NULL` and the primary key.
All `VARCHAR2` columns use byte semantics (`CHAR_USED = B`).

| NAME | VARCHAR2(100) | N | — | |

| AVATAR_URL | VARCHAR2(1000) | Y | — | |

### OTP_LOG

| Column | Type | Null | Default | Notes |
|---|---|---|---|---|
| ID | NUMBER(22) | N | identity `ISEQ$$_81354` | PK (`OTP_LOG_PK`) — generated by the database |
| USER_ID | NUMBER(22) | Y | — | The account the code was issued to. No FK constraint |
| CODE_HASH | VARCHAR2(255) | Y | — | Hex HMAC-SHA256 of the code — **never the code itself**. The key is a per-process secret, so the value cannot be reversed even with the database, and it is not comparable across restarts. NULL when `METHOD = 'TOTP'`: that code is never known to the server |
| CREATED_AT | TIMESTAMP(6) | Y | — | When the code was sent |
| EXPIRES_AT | TIMESTAMP(6) | Y | — | `CREATED_AT` + `OTP_CODE_TTL_SECONDS` |
| CONSUMED | NUMBER(1) | Y | — | `0` while the code is live, `1` once it has been used. A code that expired or was superseded stays `0` — issued and never used |
| CONSUMED_AT | TIMESTAMP(6) | Y | — | When it was used |
| PURPOSE | VARCHAR2(100) | Y | — | `login` \| `verify_contact` (see conventions) |
| METHOD | VARCHAR2(20) | Y | — | `SMS` \| `EMAIL` \| `TOTP` — how the code travelled (`TOTP` = it never left the user's device) |

- **Audit trail of issued one-time codes**, created 2026-09-24 by the project owner.
  Written by the application only (insert + the consume flag); it is **not** the
  verification store — codes are still checked against the in-process challenges in
  `OtpService`, because this table has no challenge id and must never hold anything a
  code could be recovered from.
- Rows are written once a provider has accepted the message, so the table records codes
  that really existed rather than attempts. A failed write never fails the flow — the
  history is best effort (see `docs/otp-2fa-notes.md`).

## Constraints & Indexes

- **Primary keys:** `PK_<TABLE>_ID` on every table, single-column (`ID`).
- **Contact uniqueness:** `UK_USERS_USERNAME`, `UK_USERS_MOBILE_NUMBER` and
  `UK_USERS_EMAIL` — a username, a verified mobile number and a verified email address
  each belong to exactly one account. The API checks before writing and maps a lost race
  (`ORA-00001`) to `409` rather than a 500.
- **Foreign keys:**
  - `FK_USERS_DEFAULT_MODEL_ID` — USERS.DEFAULT_MODEL_ID → AI_MODELS.ID
  - `FK_AI_MODELS_PROVIDER_ID` — AI_MODELS.PROVIDER_ID → PROVIDERS.ID
  - `FK_AI_MODELS_ENDPOINT_ID` — AI_MODELS.ENDPOINT_ID → AI_ENDPOINTS.ID
  - `FK_CONVERSATIONS_USER_ID` — CONVERSATIONS.USER_ID → USERS.ID
  - `FK_CONVERSATIONS_CHARACTER_ID` — CONVERSATIONS.CHARACTER_ID → CHARACTERS.ID
  - `FK_CONVERSATIONS_MODEL_ID` — CONVERSATIONS.MODEL_ID → AI_MODELS.ID
  - `FK_MESSAGES_CONVERSATION_ID` — MESSAGES.CONVERSATION_ID → CONVERSATIONS.ID
  - `FK_MESSAGES_REPLY_TO_ID` — MESSAGES.REPLY_TO_ID → MESSAGES.ID (self-reference; added by the reply migration)
  - `FK_MESSAGE_GENERATIONS_MESSAGE_ID` — MESSAGE_GENERATIONS.MESSAGE_ID → MESSAGES.ID
  - `FK_MESSAGE_GENERATIONS_MODEL_ID` — MESSAGE_GENERATIONS.MODEL_ID → AI_MODELS.ID
  - `FK_MEMORIES_USER_ID` — MEMORIES.USER_ID → USERS.ID
  - `FK_MEMORIES_CHARACTER_ID` — MEMORIES.CHARACTER_ID → CHARACTERS.ID
  - `FK_MEMORIES_MESSAGE_ID` — MEMORIES.MESSAGE_ID → MESSAGES.ID
- **Unique:** `UK_USERS_USERNAME` (USERS.USERNAME),
  `UK_AI_MODELS_PROVIDER_ID_MODEL_NAME` (AI_MODELS.PROVIDER_ID, MODEL_NAME, ENDPOINT_ID).
- **Check constraints:** only `NOT NULL` checks (`SYS_C*`); no domain/enum checks exist.
  Value sets of `STATUS`/`ROLE`/`MEMORY_TYPE`/`PURPOSE` are therefore **conventions defined
  by the application** (see below), not DB-enforced.
- **Indexes:** only the PK/UK unique indexes above, plus internal `SYS_IL*` domain indexes
  on the two CLOB columns (MEMORIES.CONTENT, MESSAGES.CONTENT). No secondary performance
  indexes exist; the app's queries are PK/UK-driven.
- **Sequences:** 9 identity backing sequences (`ISEQ$$_80341…80386`), cache 20, no cycle.
- **No triggers, no table/column comments.**

## Conventions the application relies on

Because there are no check constraints, the API defines and documents these value sets:

- `USERS.STATUS`: `ACTIVE` (default used by registration) | `DISABLED` (login rejected).
- `USERS.ROLE`: `ROLE_user` (DB default; the app never inserts or updates this column) |
  `ROLE_admin`. `ROLE_admin` grants full CRUD over `CHARACTERS` and `AI_MODELS` and is
  granted **only by a direct database update** — no endpoint can write `ROLE`. The
  comparison is exact and case-sensitive (`app/db/models/user.py::User.is_admin`).
- `USERS.PASSWORD_HASH` is **nullable**: an account created through Google has none until
  the user sets one, and password login is refused (not verified against anything) while
  it is NULL. `GET /me` reports `has_password` so a client can tell the two apart.
- `USERS.PREFERRED_OTP_METHOD`: `SMS` | `EMAIL` | `TOTP` (`app/core/contact.py`). NULL is
  read as `SMS`, and an unrecognised value makes the login **fail closed** (503) rather
  than pick a method the user did not choose. `SMS` and `EMAIL` need a verified
  destination; `TOTP` needs an enrolled authenticator — an account whose preference names
  a method it cannot use fails closed too, rather than substituting another one.
- `OTP_LOG.PURPOSE`: `login` (a code to sign in) | `verify_contact` (a code confirming a
  mobile number or an email address). `OTP_LOG.METHOD` reuses `USERS.PREFERRED_OTP_METHOD`'s
  `SMS` | `EMAIL` | `TOTP` — `TOTP` records that a challenge was opened for a code the
  user's own app generates, which also means `CODE_HASH` is NULL for that row (there is no
  code here to hash). `OTP_LOG.CONSUMED`: `0` | `1`.
- `CONVERSATIONS.STATUS`: `ACTIVE` | `DELETED` (**soft delete** — DELETE endpoint sets this;
  rows and messages are preserved).
- `MESSAGES.ROLE`: `user` | `assistant`.
- `CHARACTERS.STATUS`: `ACTIVE` | `DELETED` (**soft delete** — `DELETE /characters/{id}`
  sets this; the row is kept so conversations and memories keep their foreign keys).
  Only `ACTIVE` characters are listed; administrators see every status.
- `AI_MODELS.ACTIVE`: `1` | `0`. `DELETE /models/{id}` sets `0` rather than removing the
  row, which `CONVERSATIONS`/`USERS`/`MESSAGE_GENERATIONS` still reference.
- `MEMORIES.MEMORY_TYPE`: `fact` | `preference` | `event` (free-form, app passes through).
- `MEMORIES.STATUS`: `ACTIVE` | `ARCHIVED`.
- `MESSAGE_GENERATIONS.PURPOSE`: `chat`.

## Constraints the application must respect

1. `CONVERSATIONS.MODEL_ID` is NOT NULL — every new conversation must resolve a model
   (explicit request value, else the user's `DEFAULT_MODEL_ID`, else the first active model).
2. `CONVERSATIONS.CHARACTER_ID` is NOT NULL — a character must be chosen at creation.
3. `USERS.STATUS` has no DB default — registration must supply it explicitly.
4. `AI_ENDPOINTS.API_KEY` is a stored secret — never selected into API responses or logs.
5. All FK columns are NOT NULL except `USERS.DEFAULT_MODEL_ID`, `MEMORIES.MESSAGE_ID`,
   and `MESSAGES.REPLY_TO_ID`.
